# rtc-battery-probe — DS1302 纽扣电池消融探针

一次性回答：**STC-B 拔掉 USB 之后，DS1302 的钟还走不走？**

## 为什么需要它

官方 BSP `DS1302.h`（第一手资料）写的是：

> 断电后，RTC 和 NVM 是依靠纽扣电池 BAT 维持工作的
> `DS1302Init(time)`：如果 DS1302 掉电（初始化时检测 RTC 数据失效），则以参数 time 初始化 RTC

但课程期板测记录写的是「掉电检测 NVM[30] 不可靠，长时间断电后上电 RTC 被 `DS1302Init`
重置为初始化参数」。两条互相矛盾，而且**当时的固件每次上电都无条件调用
`DS1302Init(默认时间)`**——所以那次观测无法区分下面三种原因：

| | 原因 | NVM 标记 | RTC min/sec | 正确修法 |
|---|---|---|---|---|
| **A** | 电池有效，RTC 断电继续走；「被重置」是固件自伤 | 保留 | 按断电时长前进 | 固件别无条件 Init：先读芯片，合法就直接用 |
| **B** | 电池有效但 RTC 停振 | 保留 | 停住/垃圾 | 换晶振或改用 M24C02 + 上位机对时 |
| **C** | 电池没装 / 没电 | 丢失 | 丢失 | 只能靠上位机对时（+ 可选存「最后已知时间」） |

A 与 C 的修法完全相反，所以必须先做这个实验再决定固件怎么写。

## 消融设计

1. **启动路径绝不调用 `DS1302Init`**——先把「我们自己造成的破坏」从实验里拿掉。
   只有显式按 `I` 才做对照（会破坏实验状态，最后才用）。
2. 上电第一件事原样读 RTC + NVM，打印 `PRE:` 行，并把芯片时间显示在数码管上
   （不接串口也能看出钟在不在走）。
3. `NVM[21]` = 启动计数，`NVM[22]/[23]` = `0xA5/0x5A` 标记。NVM 与 RTC 都由电池保持，
   但 NVM 不依赖振荡器——两者分开判读才能把 B 从 A/C 里分出来。
4. 已知本板 DS1302 的 hour 寄存器会自发变成 bit7 置位的垃圾值（课程期实测），
   所以**判读一律以 min/sec 为准**；hour 只作为原始证据打印（`hourraw` / `hourbad`）。
5. DS1302 RTC/NVM 读写不要求先调用 `DS1302Init`；本探针启动路径直接读芯片，以实验本身复核该前提。

## 串口命令

| 命令 | 作用 |
|---|---|
| `H` | 打印帮助 |
| `R` | 读取 RTC + NVM 标记并输出 `READ:` |
| `S` | 写入基准 RTC `12:34:56` + NVM 标记 |
| `N` | 只写 NVM 标记，不碰 RTC |
| `I` | 对照调用 `DS1302Init(08:00:00)`（破坏当前实验状态） |
| `T` | 连续输出 10 拍 `TICK:` |
| `D` | 5 秒后软复位进 ISP，用于无人按键烧录 |

## 实验步骤

```bash
# 0) 先释放 COM3（停止 CloudPath Edge 或其他串口工具）；烧探针会顶掉 Full Firmware
python build.py --flash

# 1) 接串口（115200 8N1）
python ..\..\tools\serial-console.py    # 或 serial-log.py 只看输出

# 2) 设基准：写 RTC=12:34:56 + 写 NVM 标记
S
# 3) 确认振荡器在跑（连续 10 拍，min/sec 应递增）
T
# 4) 【物理步骤】拔掉 USB 5 分钟，再插回来
# 5) 看上电自动打印的 PRE: 行，按下面判读
```

## 判读

看 `PRE:` 行的三个字段（断电 5 分钟基准 `12:34:56`）：

| `markok` | `rtc` min/sec | 结论 |
|---|---|---|
| `1` | ≈ `39:5x`（前进了约 5 分钟） | **A：电池有效，钟断电继续走** → Full Firmware 应改成「先读芯片、合法就用，不无条件 Init」 |
| `1` | 停在 `34:5x` 或垃圾 | **B：电池供电但 RTC 停振** |
| `0` | 丢失/垃圾 | **C：电池没装或没电** |

`boots=` 应每次上电 +1；若断电后 `boots` 也归零，与 `markok=0` 互证 C。

## 实验结果（2026-09-08，本板）

本板实测结果如下，按证据判读为**不能依赖 DS1302 电池保持**：

- 断电前 `S`：`want=12:34:56, got=12:34:56, minok=1`，但 NVM 标记回读仍是
  `mark=FE,F8`，没有变成 `A5,5A`——**标记写入/保持链本身不可信**。
- 断电前 `T`：连续 10 拍为 `rtc=92:00:30` 到 `92:00:39`。秒在递增，但分钟不是刚写入的
  `34`，hour 仍是已知坏值 `92`；本板 DS1302 的写入/回读行为不一致。
- USB 拔掉 5 分钟以上再插回：`rtc=92:08:40/41`、`ymd=00-01-01`、`boots=AF`（与断电前相同）、
  `mark=FE,F8`、`markok=0`。上电后时间与 `DS1302Init(08:00:00)` + 已运行时间吻合，
  NVM 标记和启动计数均未体现电池保持。

**结论**：本板不能给出“A：电池有效、RTC 断电继续走”的干净证据；相反，NVM 标记写入与跨断电
保持均失败。工程上继续采用 **M24C02 持久化 + 主机对时/软件 hour**，不把 DS1302 电池保持作为
可靠性前提。若要继续做芯片级区分，应先换 DS1302/纽扣电池或修板，不阻塞当前大作业。

> 注：串口重插后重新枚举 COM3 会错过 `PRE:` 的首批字节，本次以上电后的 `R` 回读为准；
> 该边界不影响上述结论。
